## 2026-09-24: Risk audit -> fan worker deadlock, runtime-lock hole, install fan freeze

A code-reading audit ranked the riskiest areas and the recommendable targeted
fixes were implemented:

- **Fan worker self-stop deadlock (fixed).** Windows fan escalation ran under
  `g_appLock` and stopped the fan worker from inside it; the self-join released
  the runtime mutex for 5 s and re-took it still holding `g_appLock` -> ABBA
  with any telemetry request -> wedge watchdog emergency restart. Also did NVML
  writes under `g_appLock`. Now signal-only self-stop plus escalation outside
  the lock. See [fan-control](../fan-control.md#windows-service-fan-worker-lifecycle-2026-09-24).
- **Runtime-lock hole (fixed).** `stop_service_fan_runtime_thread()` dropped the
  runtime mutex mid-Apply/Reset; lifecycle restores and the updater serialize
  on that mutex only, so they could interleave a full transaction. The worker's
  wait is now cancellable by its stop event and stoppers keep the mutex.
- **Unsynchronized worker handle (fixed).** Main-thread startup/shutdown/
  watchdog now own the handle under the runtime mutex (watchdog via try-lock).
- **Install froze manual fans (fixed).** See [updates](../updates.md#fans-during-an-install-2026-09-24).
- **Small:** pending-restore log path tokenized; an out-of-range VF batch
  refusal is no longer counted twice in apply.

Deliberately NOT done: a fake-driver harness for `apply_desired_settings_service`
(the only fake driver is the Linux transition fixture; faking NVAPI's private VF
structs for the Windows amalgamation is a large project, not a targeted fix);
a thermal fan failsafe (changes configured semantics -- product decision);
suspended setup launch (AV heuristic cost, see updates.md). The 1,440-line
apply function remains the highest-churn untested code.

Verification: `python build.py --test` (6300-6332, mutation-checked) and the
full `python build.py` matrix passed. No hardware or live-install run; the
deadlock was established from lock order, not reproduced.

## 2026-09-22: install-anywhere with informed consent replaces the Program Files gate

The "direct child of Program Files" installer rule is gone; the real F-SEC-1
property is now proven directly and everything weaker is an acknowledged
administrator decision (installer.md "Where may it be installed?").

Design facts worth keeping:
- The property is per path component: admin/SYSTEM-owned, non-reparse, no
  delete / delete-child / WRITE_DAC / WRITE_OWNER grant to any non-admin.
  Create-only grants are harmless; a volume root ignores a bare DELETE grant.
  Real default ACLs forced both nuances: `C:\` hands Authenticated Users
  inherit-only Modify (counting it would warn on the DEFAULT install path),
  and `D:\` hands them Modify at the root and inheritable — so a folder
  created under a data-drive root inherits DELETE and can be renamed away and
  replaced even while its child carries a hardened DACL. That rename-away
  vector is why a bare DELETE grant on a non-root component is dangerous and
  why the missing-tail rule checks inherit-only ACEs.
- Unproven is never "protected" (the fail-safe direction); the consent
  sentence names the SYSTEM escalation verbatim and is pinned by gates.
- Silent runs (the updater) never block on the acknowledgment — unattended
  machines must never stall behind a session-0 dialog. The verdict is logged
  and surfaced as a GUI status warning instead.
- UNC paths short-circuit before any probe: server-controlled is the verdict,
  and a dead share must not stall the folder page's live classification.
- FAT/exFAT is a loud capability gap (DACL hardening skipped and logged), not
  a mysterious SetNamedSecurityInfo failure.
- The failing folder gets a shown-never-applied icacls recipe; the
  mkdir-and-icacls spelling exists because the folder to protect is often the
  one that does not exist yet.
- Admin-trust resolves SYSTEM/Administrators/TrustedInstaller plus direct
  members of the local Administrators group (localized name resolved from the
  SID — German Windows calls it "Administratoren"); nested domain membership
  classifies untrusted (warns, fail-safe). Owner Rights SID resolved by
  string (S-1-3-4) for older SDK headers.

Verification: `--test` (pure matrix 5400-5429/5458-5463, walker fixtures
5430-5457 incl. junction reparse + UNC short-circuit + read-only Program Files

## 2026-09-17: 0.26.0 release prep — the handoff nobody tests

Prepping the 0.26.0 release turned up that the one thing an update genuinely
has to get right had no executing test at all.

**The cross-version curve handoff.** The in-app update is the only place two
different releases exchange a curve, and it runs in exactly one direction: the
installed 0.25.2 GUI writes `pending-update-restore.ini`, the freshly installed
0.26.0 GUI reads it back through `--apply-settings-file`. 0.25.2's exporter
writes BASE MHz under `curve_semantics=base_plus_gpu_offset` whenever the
capture carries a nonzero GPU offset; 0.26.0 writes absolute MHz under
`absolute_with_origin`. Reading the old shape with the new rule would take
2322 MHz as a typed absolute, apply a curve 475 MHz below the one that was
running, and report success. The reader is the only side that can be fixed,
because the writer is already on the user's machine.

The code was correct — [main_shell.cpp](../../source/main_shell.cpp) runs the
same two-step the slot loader does (per-point provenance first, legacy
whole-section reconstruction only when that declines). Nothing executed it.
Assertions 5200-5216 now do, against a real INI file in the exact byte shape
0.25.2 emits. **Mutation tested**: dropping the `+ offsetCompMHz` add-back in
`restore_curve_points_from_base_plus_gpu_offset()` fails 5207 and nothing else.

**`0.26` and `0.26.0` are the same version, and that is load-bearing.** An
absent patch component parses as zero, so `gc_update_version_compare()` calls
them equal — a machine on either spelling is UP_TO_DATE against the other, and
`gc_update_restore_decide()` accepts a capture bound to one while running the
other. What is NOT interchangeable is the manifest's literal `version=` text,
because the asset filename is built from it. Written down because the release
was nearly cut under the short spelling and the wrong intuition (that `0.26`
sorts below `0.26.0`) survived into a first draft of the test, where 5218
caught it. Assertions 5217-5221, plus 4319/4326 pinning the filename.

0.24.0 -> 0.25.0. It now covers the whole public updater-bearing population

manifest, plus UP_TO_DATE for 0.26.0, REJECTED for 0.27 (the local test tags),

## 2026-09-17: the version number was never the layout

Second 0.26.0 release review, this one from an outside audit. Three findings,
all real, and the first two were release blockers.

**The persisted records.** Adding `curvePointFromGpuOffset[128]` took
`DesiredSettings` from 836 to 964 bytes. The IPC protocol was bumped (25 -> 27);
the three files that embed the struct as raw bytes were not. Their loaders gate
on `size == sizeof(CurrentStruct)`, so a 0.25.2 Linux upgrade deletes the
restore-last record and downgrades the startup policy to `NONE` — and the Arch
`post_upgrade` try-restarts a running daemon, so it happens immediately, with
only a `dlog` line nobody reads.

Digging into it turned up the bigger fact: **no on-disk version number in this
project has ever tracked its layout.** `SERVICE_ACTIVE_DESIRED_VERSION` has been
5 since 0.19.2 across several payload layouts; `LINUX_DAEMON_RECORD_VERSION` was
1 across at least three (XBAR, SYS clock, video clock all landed inside that
window). So every "backward-compatible vN" branch was declared over the LIVE
struct and was unreachable code that could never once have fired —
`SERVICE_ACTIVE_DESIRED_LEGACY_VERSION 4u` and `LinuxDaemonStateRecordV1` both.
The fix is a rule, not a patch: SIZE selects the layout, VERSION selects the
semantics within it. Frozen `DesiredSettingsSchema1` + frozen record layouts +
widening migrations + `static_assert`s on every record size that name the four
version constants to bump. See [persistence-schema](../persistence-schema.md).

**The saved curve.** `curve_semantics` was a WHOLE-SECTION statement, so the
mixed profile the per-point provenance work exists for — one hand-typed point
among projected neighbours — could not be written down. Save flattened it and
load marked every point offset-derived, so one save/reload cycle handed a number
the user typed back to a base that moves a whole VF bin under load. New format
`absolute_with_origin`: absolute MHz plus `pointN_from_gpu_offset` per point.
Chosen partly because it downgrades safely — an old build reads an unknown
marker as absolute, which is right; writing base MHz under a marker it DOES know
would have re-added an offset the new file no longer subtracted.

**The validator.** `curvePointFromGpuOffset[]` reached the wire struct and the
canonicalizer but not the strict pre-canonicalization boolean check. Not
exploitable — 2 folds to true — which is exactly why it would have stayed
invisible.

Notes for next time:
- The old migration suite built the CURRENT structs and relabelled their
  version numbers. It passed throughout. Fixtures for a layout migration have to
  be byte-exact or they test nothing; `desired_settings_narrow_to_schema1()`
  exists only for the harness.
- `main()` in `tests/regression_main.cpp` is close to the ASan stack limit. The
  frozen records (>1 KiB each, several live at once) overflowed it; the suite
  now lives in `run_persistence_schema_tests()`. Assume the same for any future
  large-struct suite.
- Three files hit the source-size ratchet on the way through, which forced four
  splits that were overdue anyway: `service_protocol_wire_validation.h`,
  `service_restart_snapshot_schema.h`, `linux_profile_curve_codec.h`,
  `profile_curve_origin_io.h`. build.py hit its own ratchet too, hence
  `tools/persistence_gates.py`.
- **Stale-risk:** all of this is software-only. No real 0.25.2 -> 0.26.0 Linux
  upgrade and no mixed-provenance save/reload/apply have been run on hardware.
  Those are the two release acceptance scenarios still outstanding.

Validation: `build.py --test`, `--test --asan`, `--tidy` (no new findings, 34
baselined) and a full `build.py` (Windows x64/ARM64, Linux x64/ARM64, both Arch
packages) all pass. Each of the three new test groups was verified failing with
its fix reverted (2016, 5077, 5030).

The VF curve read back 3592 MHz while the GPU ran 2910 MHz at 99% load. Across

Two design choices were validated by the data rather than by argument:
- One run's judged peak landed at stage **`curve settle`** (14:27:27), i.e. in
  the MIDDLE of the post-curve window rather than at either end. That is exactly
  the case the settle-loop polling hook was added for; sampling only the window's
  two ends would have missed it.
- `post-reset settle` reads **2677 MHz** at 249.9 W: during the 1 s stock-curve
  settle the board power-throttles, because stock asks more voltage for a given
  clock. Expected, and harmless -- clocks only fall there.

**Second defect in the witness, again found by the runs and not by reading.**
Three of the seven judged peaks landed at stage `ceiling armed` -- a sample taken
in the same instant the arming call returns. No clamp takes effect between an
NVML write returning and the next statement, so that reading is still the
pre-clamp clock; each of the three read *exactly* its `preArmPeak` value (2932,
2917, 2902 MHz). They passed only because the outgoing clocks happened to sit
under the incoming ceiling. A profile switch that LOWERS the ceiling (say
3000 MHz -> a 2500 MHz pin) would have reported `EXCEEDED` for a clock the clamp
had not yet had any chance to cap -- a false alarm in the one line meant to be
authoritative, and the same bug as yesterday's `apply entry` case one sample
deeper.

Fixed by making the rule name the sample SITE rather than a moment in time:
`apply_clock_witness_counts_toward_verdict(clampArmed, sampledAtArmingInstant)`,
with `apply_clock_witness_record_at_arming()` as the separate entry point the
guard uses. A "wait a moment before judging" rule would have been a timing
assumption, which this project refuses -- and would have been the wrong
statement anyway: the sample is *contemporaneous with the write*, not merely
early. Each per-stage line now also carries `judged=0/1`, so a reader never has
to work out why a high sample did not trip the verdict. Tests 5242-5243.

## 2026-09-13 (under load): F-APPLY-CEILING confirmed on hardware — the clamp holds while the curve sits 712 MHz above it

**The result.** Four profile 3 <-> 4 applies with a game running
(`loadMeaningful=1`), all `-> HELD`, no `nvlddmkm` event. The decisive trace is
the 14:18:46 apply, at the exact instant that crashed the driver on 13:43:55:

```
14:18:43.448  apply ceiling: armed 0..2957 MHz before the first clock write
14:18:45.607  [post-reset settle]        gpc=2902 MHz util=50% power=150.2 W temp=50 C
14:18:46.635  [post-curve-batch (pre-lock)] gpc=2925 MHz util=52% power=128.8 W temp=47 C
14:18:46.791  apply curve peak after batch: 3637 MHz at ci=125; clamp armed=1 at 2957 MHz
14:18:46.793  nvml_set_gpu_locked_clocks: min=2957 max=2957 ok
14:18:46.835  verdict: peak gpc=2925 MHz (at post-curve-batch (pre-lock)) vs
              ceiling=2957 MHz armed=1 -> HELD; load peak util=52% power=150.7 W
              temp=50 C loadMeaningful=1 samples=15
```

The VF curve read back **3637 MHz** at ci=125 while the GPU ran **2925 MHz**
under active 3D load. That is the mechanism working: NVML locked clocks DO hold
the GPC clock during a VF table rewrite on this driver (580-series era,
Blackwell), which was the open question.

**Why this closes the load-dependence question rather than merely surviving it.**
The old failure was never "load makes an apply crash at random". It was that the
apply created a genuinely out-of-spec operating point -- 3637 MHz on a board
stable to 2957 -- and whether that particular excursion killed the driver
depended on what the GPU happened to be doing. With the clamp holding, the
out-of-spec operating point no longer exists at any moment of the apply, so the
load dependence is removed rather than untested. Four clean runs would be weak
evidence on their own (the original crash was roughly 1-in-several); the clock
reading during the window is the strong evidence.

**A defect in the new diagnostic, found in these very runs.** Two of the four
verdicts reported their peak at stage `apply entry` -- a sample the witness takes
deliberately BEFORE the clamp is armed, to record what the outgoing profile was
running. Those readings were 2932 MHz against a 2957 MHz ceiling: HELD, but only
just. A slightly higher outgoing profile (or switching away from an unpinned
one boosting to 3600) would have folded a pre-clamp clock into the judged peak
and reported `EXCEEDED` for a clock the clamp was never in a position to cap --
a false alarm in the one line meant to be authoritative. Fixed:
`apply_clock_witness_counts_toward_verdict()` (pure, tested at 5240-5241) keeps
pre-arm samples in a separate `preArmPeak=` field that is reported for context
and never judged.

**Still worth a note:** the load was moderate -- util 50-54%, 145-150 W of a
250 W board, 46-54 C -- against 48-63 C in the crash window. Heavier sustained
load has not been tried. Given the argument above this is a completeness gap
rather than a correctness one, but a maximal-load run would be the last word.

## 2026-09-13 (later): the first post-fix test ran idle, so the apply now witnesses its own clock and load

**What happened.** Seven profile 3 <-> 4 applies were run against the
F-APPLY-CEILING build (13:54 -> 14:08), including four rapid flatten<->hard
alternations in 28 s. No `nvlddmkm` event, no `COULD NOT ARM`, no

```
14:07:35.230  apply ceiling: armed 0..2957 MHz before the first clock write

              transition clamp armed=1 at 2957 MHz (lockMode=hard)
14:07:38.608  apply ceiling: clamp adopted (re-asserted as the final hard pin)
```

Useful facts established: the driver **accepts the open-ended `(0, ceiling)`
form**, so the symmetric fallback is not needed on this driver; the raised curve
still peaks at **3652 MHz** (higher than the 3637 in the crash log), so the
transient is real and reproducible and only the clamp is new; FLATTEN peaks at
2947 MHz at ci=76, confirming its batch really is atomic; and apply duration did
not regress (the standalone applies got *faster*, 2.45 s vs 3.48 s, because the
power write moved into the reset phase and the second write is skipped).

**The problem with that result.** GPU temperature was 34-36 C flat across the
whole window, versus 41-63 C during the crash. There was no game running, so the
load condition was never exercised -- and the original crash did not reproduce
every time either. "Nothing crashed" is what the pre-fix code did most of the
time too. Worse, discovering the run was idle required reading
`service_runtime_pulse_done` temperature lines afterwards and inferring, because
nothing in the apply trace recorded load at all.

**Fix: the apply-clock witness.** `source/apply_clock_witness.h` (Windows) and
`linux_apply_log_clock_witness()` in `source/linux_apply_ceiling.h` sample the
live GPC/SM/memory clock, GPU utilisation, board power and temperature at the
named transitions, and end with one verdict line:

```
apply clock witness verdict: peak gpc=2940 MHz (at post-curve-batch (pre-lock))
  vs ceiling=2957 MHz armed=1 -> HELD; load peak util=97% power=243.1 W
  temp=61 C loadMeaningful=1 samples=9
```

- Sample points: `apply entry`, `ceiling armed`, `post-reset settle`,
  **`post-curve-batch (pre-lock)`** (the instant that used to be uncapped), and
  `post-lock`. The existing `read_live_curve_snapshot_settled()` loop also folds
  a silent sample per iteration, which is the only thing that covers the MIDDLE
  of the ~175 ms window rather than just its two ends -- it adds one NVML read
  to an iteration the loop already made, and no sleep, attempt, or branch that
  can change what the loop returns.
- **No sampling thread, deliberately.** A concurrent NVML reader alongside an
  in-flight NvAPI VF write would add exactly the racy, timing-sensitive
  behaviour this project refuses, in the one code path whose stability is under
  investigation. Gated by `forbid_text(witness_h, "CreateThread")`.
- The verdict rule is pure and shared (`apply_clock_witness_verdict()` in
  `apply_clock_ceiling_policy.h`) so the two platforms cannot disagree about
  what "held" means. It distinguishes HELD, **HELD (driver rounded up one bin)**
  -- NVIDIA rounds a locked-clock request to a supported bin and Blackwell's VF
  table steps in 15 MHz -- and EXCEEDED. A wider tolerance would hide the
  failure the witness exists to catch.
- `loadMeaningful` (>= 20% GPU utilisation) is stated explicitly, and an idle
  run prints "a clean result here does NOT clear the under-load case". Unknown
  utilisation is never upgraded to load.

New NVML entry points resolved on both platforms, both optional:
`nvmlDeviceGetUtilizationRates`, `nvmlDeviceGetPowerUsage`.

## 2026-09-13: a profile switch under load crashed the driver, because the apply raised the curve before it capped the clock (F-APPLY-CEILING)

**Reported:** switching profile 3 -> profile 4 and pressing Apply while a game
was running crashed the display driver. The clocks each profile asks for are
known-stable, including the high VRAM clocks, so the suspicion was the *way*
settings get applied. It was.

**Evidence** (`%LOCALAPPDATA%\Green Curve\greencurve_debug.txt`, 0.25.2 build 178
era, RTX 50-series/Blackwell, plus Windows System log `nvlddmkm` event 153 at
13:43:57):

| time | what |
|---|---|
| 13:43:24 | profile 3 applied, `lockMode=flatten`, and at 13:43:28.737 `nvml_reset_gpu_locked_clocks: ok` -- FLATTEN holds its ceiling with the VF tail floor, so **no NVML pin is armed** afterwards |
| 13:43:53.0 | profile 4 Apply begins. Reset-to-stock zeroes 57 curve offsets: the flatten floor, the only thing capping the tail, is gone |
| 13:43:54.2 | `1000ms settle at stock baseline` |
| 13:43:55.2 | `curve strategy: selective=+475 MHz excl<N ... lockMode=hard boost-via-selective`; the batch writes +475 MHz to points 70..126. HARD mode does **not** floor the tail (only FLATTEN does), so the tail carries the full offset |
| 13:43:56.2 | batch returns; readback `post-apply curve: ci=76 actual=2947 ... ci=126 actual=3637` -- every tail point `freqOffs=475000` |
| 13:43:56.384 | `nvml_set_gpu_locked_clocks: min=2957 max=2957 ok` -- the pin lands **1.21 s** after the curve went up |
| 13:43:57 | `nvlddmkm` event 153 |

So for 1.21 s under game load the GPU ran a curve topping out at **3637 MHz**
with nothing capping it, at 100% power and +3000 MHz memory. 2957 MHz is stable
on this board; 3637 MHz is not.

**The control experiment is in the same log.** The 13:42:42 apply was HARD ->
HARD: the previous profile's pin was still armed (a HARD request never calls
`nvml_reset_gpu_locked_clocks`), the identical curve batch ran underneath it,
and nothing crashed. Only the *unpinned* transition -- FLATTEN/none -> HARD --
has the window. That also explains why this is intermittent rather than constant.

**Root cause:** the lock was the LAST clock write of the apply, on both
platforms. Windows: `gpu_backend_apply.cpp` pins after the curve batch. Linux:
`linux_execute_transaction()` ordered `RESET_BASELINE ... CURVE, LOCK`, and
`RESET_BASELINE` *unconditionally* released the locked clocks on its way past.

**Fix (F-APPLY-CEILING):** `source/apply_clock_ceiling_policy.h` is the one
shared decision -- when a request declares a lock target, that target is a
ceiling the user has already validated, so arm it as an NVML locked-clock clamp
BEFORE the first clock-affecting write and hold it until the final lock step.
- Ceiling, not pin: `SetGpuLockedClocks(0, ceiling)` caps without forcing the
  clock up at idle, with `(ceiling, ceiling)` as the driver-refusal fallback.
- HARD requests: the final pin is a re-assertion of the same number.
- FLATTEN requests: the existing `nvml_reset_gpu_locked_clocks` at the end of
  the apply IS the release, by which time the flattened tail is the ceiling.
  Flatten's own batch is atomic, but the reset ahead of it is not, and the
  per-point fallback inside `apply_curve_offsets_verified()` walks points in
  ascending index order -- boost before tail.
- Windows: `ApplyClockCeilingGuard` in `source/gpu_backend_apply_ceiling.h`,
  scope-bound, `adopt()`/`retain()`/destructor-release.
- Linux: new `LINUX_MUTATION_LOCK_CEILING` phase, first in the transaction
  order; `RESET_BASELINE` no longer releases a clamp it is supposed to run
  under (`source/linux_apply_ceiling.h`).

**Two fixes that ride along, both found while reading the same window:**
1. **Power bounced through the board default.** `reset_oc_before_gui_apply()`
   wrote `POWER_LIMIT_DEFAULT_PCT` and the profile's own target was only written
   at the very END of the apply, after the curve and the lock. A profile that
   LOWERS the power limit therefore ran the entire apply -- reset, 1 s settle,
   and the curve batch that raises the curve -- at 100% TGP. Power is an
   absolute percentage with no stale baseline to clear, so the reset phase now
   writes the target the apply will end at
   (`power_reset_before_apply_target_pct()`). Visible in the 13:43:28 apply:
   `read_power_limit: ... -> 100%` at reset, `-> 85%` four seconds later.
2. **Rollback left a pin standing.** `rollback_to_safe_defaults()` released
   locked clocks only `if (g_app.lockMode == LOCK_MODE_HARD)`. It returns curve,
   both offsets, power and fans to stock, so any clamp left behind is an
   invisible cap -- and the new FLATTEN-mode transition clamp lives outside
   `LOCK_MODE_HARD` by construction. Now unconditional.

**Diagnostics added:** `apply ceiling: plan arm=... ceiling=... finalPin=...`,
`apply ceiling: armed/adopted/KEEPING/released`, and
`apply curve peak after batch: <peak> MHz at ci=N; transition clamp armed=...`
with an explicit WARNING when a peak exceeds the requested lock with no clamp.
Reconstructing this incident needed 51 hand-summed per-point readback lines;
the peak line answers it directly.

**Tests:** 5200-5204 (power reset target), 5205-5215 (ceiling plan table and the
abandon rule), 5216-5225 (Linux phase ordering, verified to fail -- code 5218 --
when `LINUX_MUTATION_LOCK_CEILING` is moved back to the end of the order).
Source gates in `tools/apply_ceiling_gates.py`; every rule there guards an
ordering, which is exactly the kind of property whose loss leaves the apply
reporting `severity=success`.

**Open / unverified:** the fix is reasoned from the log above and is not yet
confirmed by repeating the FLATTEN -> HARD switch under load on the real GPU.
Whether the driver accepts a 0 minimum in `SetGpuLockedClocks` on this driver
version is likewise unverified on hardware -- the symmetric fallback exists for
that, and the log says which one armed.
